# Opportunity313 iOS

Opportunity313 connects Detroit youth and families with reviewed opportunities.
This native SwiftUI app is the Venture313 core MVP and shares the existing
Supabase backend with the web project.

## Account and age model

- Ages 18–24 may create and own an independent young-adult account.
- Anyone under 18 uses a parent-managed youth profile; they do not create a
  standalone account.
- A parent or guardian may create, replace, or revoke a private child access
  code. The code opens only that child's profile and may be used to adjust
  interests and browse age-eligible opportunities.
- Parent-controlled information, guardian relationships, consent, saves, and
  spending decisions remain attached to the parent-managed profile.
- Home and Discover filter opportunities against the active profile's age,
  grade, and gender eligibility. Parents choose the child they are currently
  browsing for. Providers mark programs as co-ed/all, boys, or girls; co-ed and
  unspecified legacy programs remain visible to everyone. Saving a parent's
  gender change refreshes the active child and immediately removes incompatible
  opportunities from Discover, recommendations, and the family calendar.

The interface follows the device appearance. It uses semantic iOS backgrounds,
labels, separators, and controls for Light and Dark Mode; fixed white text is
limited to high-contrast orange selections and image-overlay cards. Opportunity
cards use an elevated warm surface, orange edge, and shadow in Dark Mode so they
remain visually distinct from the darker page background.

Accessibility is treated as a product requirement. Opportunity cards support
Dynamic Type without clipping at accessibility sizes, meaningful controls have
VoiceOver labels and hints, interactive controls preserve 44-point targets,
animations respect Reduce Motion, and information is not communicated by color
alone. Validate both appearances and accessibility text sizes before release.

Access codes are generated by the `child-access` Supabase Edge Function. Only a
SHA-256 digest and a short hint are stored in `child_access_credentials`; the
plain code is returned once. Revocation unlinks the child auth identity before
removing it, so an existing session no longer satisfies youth-profile RLS.

## Agreed MVP

- Adult email/password sign-in, signup confirmation and resend, role onboarding.
- Parent-generated child access-code sign-in for users under 18.
- Youth profile setup/editing, opportunity discovery and filters, saves, calendar.
- Parent-managed youth profiles, per-child saves, family calendar.
- Provider organization setup, opportunity submissions and review status.
- Admin detailed review, provider verification, approval and publication.

Provider Events displays the schedule of the organization's submitted
opportunities. As of September 22, Event Tickets also connects the existing
athletics event backend to the native app: free reservations, QR confirmations,
owner ticket history/cancellation, and authorized event-staff check-in. Open
Profile → Event Tickets as a parent or youth. Athletics staff use Events; admins
use Check-In. Existing demo events stay explicitly labeled.

See [ticketing implementation and validation](docs/TICKETING.md).

## Run

Open `Opportunity313.xcodeproj` in Xcode 27. Select the Opportunity313 scheme
and an iPhone or iPad Simulator, then Build or Run. Test with Product → Test.
The app targets iPhone and iPad on iOS/iPadOS 17 or later. The signing team is unchanged.
Swift dependencies are pinned by the committed `Package.resolved`.

## Competition website

The public project website is a responsive static showcase in `website/` and is
deployed by Netlify using `netlify.toml`. It explains the product model, includes
an interactive age/profile demonstration, documents the family access approach,
and highlights accessibility and engineering decisions. Changes pushed to the
connected GitHub repository deploy automatically to
`https://opportunity313.netlify.app`.

## Architecture and configuration

SwiftUI features call main-actor service objects using `supabase-swift`.
Supabase tables, RLS policies, RPC functions, and the `child-access` Edge
Function remain authoritative for ownership, roles, provider verification,
child access, and publication.

`SupabaseManager.swift` contains the existing project URL and client publishable
key. A publishable key is client configuration, not an administrator credential.
Never put service-role keys, secret keys, account passwords, or private signing
material in the app or repository. Git ignores local credentials, build data,
and Xcode user state.

## Validation

See `docs/VALIDATION.md` for evidence and remaining UI rehearsal coverage.
`python3 scripts/check_accounts.py --help` describes the read-only authenticated
account check. It prompts for a password and keeps it only in memory.

`scripts/check_mvp_rollback.sql` exercises the backend product loop under the
existing authenticated roles and rolls back all test writes. Run the whole file
as one transaction using an administrator SQL connection; never execute only
selected statements. It expects one demo account per MVP role and a provider
organization and youth profile already configured.

The optional four-role UI test reads `MVP_TEST_PASSWORD`, `MVP_YOUTH_EMAIL`,
`MVP_PARENT_EMAIL`, `MVP_PROVIDER_EMAIL`, and `MVP_ADMIN_EMAIL` from the test
runner's environment. It skips when credentials are absent. Do not commit
credential-bearing schemes or test fixtures.

## Verified resource data

The current source review is documented in
`docs/resources/opportunity313_verified_resources_2026-09-19.md`. Its companion
`docs/resources/opportunity313_resource_candidates.json` contains staging
records prepared for review and import. The file intentionally keeps unknown
dates, locations, and eligibility values empty instead of guessing. Only
records whose registration details are still current should be published;
closed, expired, or underspecified programs remain on the watchlist.

`scripts/import_verified_official_resources.sql` is the reviewed, idempotent
production import for the currently selected first-party listings. It creates
verified provider records, publishes the official opportunities with stable
IDs, and allows `starts_at` to be empty for genuinely ongoing services. Run it
as one transaction in the Supabase SQL editor, then verify the public feed
before presenting or releasing the app.

## Deferred launch requirements

Terms & Conditions and a Privacy Policy are intentionally deferred until after
the competition. Before a public production launch, publish both documents at
stable public HTTPS URLs and link them from signup, account settings, and the
App Store listing. The privacy policy should specifically describe
parent-managed child profiles, access codes, consent, data retention, account
deletion, and the providers that process app data. Do not ship placeholder
legal acceptance language as though it were final legal advice.
