# Opportunity publication and phone alerts

Provider submits → Pending review → Admin approves → Published in the shared Supabase opportunities table → Public listing in iPhone and Android → One queued phone alert to users who enable alerts.

## What is connected

The iPhone app reads only published opportunities. The existing database policy also excludes expired registration deadlines. Home and Discover refresh when the app returns to the foreground, in addition to existing initial-load/pull-to-refresh behavior.

The Android project at `../Opportunity313Android` now has **Browse approved opportunities** on its sign-in screen. This public reader uses the exact same backend/project and publication policy as iPhone. It includes category/search, provider details when public, nullable ages, provider timezone, exact currency, live details and external registration links. It refreshes on resume or Refresh. Failed refresh clears stale results rather than substituting sample data. Sample listings are explicitly labeled and cannot launch registrations. The separate debug demo remains in memory; Android account login/profile management still needs its production adapter. The sibling Android directory currently has no Git repository/remote; the iOS commit does not claim to publish its source.

## Notification implementation

Both apps integrate Firebase Messaging and subscribe, after explicit opt-in and OS permission, to `published_opportunities`. This is a **public broadcast**, independent of account role and suitable only for public listings. It is not a private family, targeted matching, ticket or school notification channel. No child/profile data is included. Users can disable alerts; app controls surface subscription failures and offer system settings. Firebase auto-init is disabled until opt-in. Tapping an alert opens its opportunity; withdrawn/expired listings show an unavailable state through the public access rules. The Android foreground handler creates the same notification channel used by background delivery.

`opportunity_push_events` has a unique opportunity ID, RLS with no client grants, private enqueue trigger, bounded leased claims, backoff and six-attempt failure handling. Only first publication of non-demo, unexpired opportunities queues an event. Ordinary edits and reapproval do not send another alert. There is no historical backfill. The worker rechecks public status before sending, skips old (>24 hours), demo and expired events, and sends through Firebase HTTP v1 with Android and APNs payload settings. A later withdrawal can race with an already accepted push; opening it rechecks visibility. Firebase accepting a topic message does not guarantee every device receives it. Collapse/tag fields reduce duplicate presentation, but retries after network uncertainty are not an exactly-once delivery guarantee. Terminal failures require review.

The migration and edge function are deployed. **The scheduler is inactive and push delivery is not live.** No Firebase project, client configuration, service credential, APNs key, signed push build or real phone delivery has been configured/verified.

## Activate before promising push delivery

1. Create one Firebase project owned by Opportunity313. Register Apple bundle ID `com.Kevin.Opportunity313`, Android release package `com.opportunity313.android`, and debug package `com.opportunity313.android.debug` if testing debug builds. Existing Android IDs remain provisional; confirm before store registration.
2. Put the Apple `GoogleService-Info.plist` in the app's `Opportunity313/` folder/target. Put Android configurations in `app/src/debug/google-services.json` and `app/src/release/google-services.json`. The pinned Google Services plugin applies when a configuration file exists; builds without it remain usable for public browsing and display honest setup status. These files are client configuration, never server credentials.
3. Enable Push Notifications for the Apple App ID/provisioning, generate an APNs authentication key in Apple Developer, and upload it to Firebase Cloud Messaging with the correct key/team IDs. The app declares development APNs entitlement for Debug and production for Release/TestFlight. Verify the signed archive's entitlements. Do not commit the APNs private key.
4. Enable Firebase Cloud Messaging HTTP v1 and use a least-privileged service account authorized to send messages. Store its JSON only as the Supabase Edge Function secret `FIREBASE_SERVICE_ACCOUNT_JSON`. Do not put it in either app, browser code, Git, or chat. The worker authenticates privately using its Vault-backed dispatch secret; public requests receive 401.
5. On a physical iPhone signed for APNs and a Google Play-enabled Android device, opt in, confirm permission, then approve one clearly identified QA opportunity with approved testers. Verify the alert appears in foreground/background and cold-start, tapping opens the right opportunity, opt-out stops alerts, and pending/rejected/demo/expired records never broadcast. Review provider acceptance separately from actual device delivery.
6. After the checks, enable `op313-opportunity-push` using `cron.alter_job`. Review/skip stale queued events first; the worker also suppresses events older than 24 hours. Monitor failed events, rotate credentials appropriately, and update App Store/Play privacy disclosures for Firebase installation/messaging data.

Official setup references: [Firebase Apple client](https://firebase.google.com/docs/cloud-messaging/ios/get-started), [Firebase Android client](https://firebase.google.com/docs/cloud-messaging/android/get-started), [HTTP v1 server authorization](https://firebase.google.com/docs/cloud-messaging/send/v1-api), [public topic behavior](https://firebase.google.com/docs/cloud-messaging/topic-messaging).

## Verification

- Server rollback check: provider cannot directly publish; pending is private; admin approval is public and queues exactly one real/nonexpired alert; demo/expired excluded; private queue and inactive cron; matching leases, backoff and old-event suppression. All test writes rolled back.
- Worker fixtures: real RSA signing against a mocked OAuth response; both-platform payloads; unauthorized/wrong-secret requests; missing configuration preserves attempts; accepted, retry and permanent sender failures; suppression of unavailable/demo/expired/old records. No real notifications sent.
- Android exact anonymous REST request returned 12 approved, unexpired listings at verification time, from the iPhone backend. Android mapper tests cover nullable eligibility, provider visibility fallback, publication/deadline filtering, timezone and currency.
- Android Debug and unsigned Release builds, all 12 unit tests, lint (0 errors, 21 advisory warnings), and both emulator tests passed. Live catalog and detail screenshots were inspected at 1080×2400. The emulator could not resolve the Supabase hostname directly, so the live test used a temporary, Supabase-only HTTPS tunnel through the Mac; the proxy was removed afterward. This does not verify network behavior on a physical phone. iPhone unsigned Release build and all 35 app unit tests passed with normal simulator signing. The Keychain test requires signing; disabling signing for an earlier test run caused that test to fail. The security advisor's new no-policy INFO for the queue is intentional deny-all client access. Older SECURITY DEFINER/Auth warnings remain outside this change; this is not a comprehensive security audit.
